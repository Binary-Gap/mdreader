# MDReader

Native macOS markdown reader: a WKWebView in a `NSWindow`, vim-style key bindings, warm "reading-lamp" dark theme (plus a warm-paper light theme, `Cmd+Shift+D` to toggle). Swift app generated from `project.yml` via xcodegen.

## Layout
- `Sources/MDReader/` - app source (AppDelegate, MainWindowController, MarkdownRenderer, NavBar, Theme, Keybindings, SidebarViewController, MDReaderSchemeHandler).
- `MainWindowController` is split across four files (all globbed by xcodegen): `MainWindowController.swift` (class decl, stored props, layout constants, init/deinit, window/view setup, hamburger styling, `windowTitle`), `MainWindowController+Navigation.swift` (nav/chrome glue: `loadMDReader`/`loadInitial`/`openFile`/`navigate`, `syncChromeFromURL`, back/forward, address bar, `WKNavigationDelegate` + `NavBarDelegate` conformances), `MainWindowController+Keys.swift` (key monitor, `perform`, scroll/zoom/always-on-top), `MainWindowController+Sidebar.swift` (sidebar toggle, hamburger proximity, `SidebarViewControllerDelegate`).
- `MDReaderSchemeHandler.swift` - `WKURLSchemeHandler` serving `mdreader://` URLs as themed HTML (see Navigation).
- `FileWatcher.swift` - single-file `DispatchSource` watcher powering live reload (see Live reload).
- `Theme.swift` - all colors/typography as override-able tokens. CSS (incl. `::-webkit-scrollbar`) emitted from `css()`; syntax-highlight token colors from `highlightCSS()`. Two built-in variants (see Theming below), both fully `Codable`. User partial override merges from `~/.config/mdreader/theme.json` on top of whichever variant is active.
- `MainWindowController` - standard macOS titled window (`.titled .closable .resizable .miniaturizable`); the webview is the contentView below the system titlebar, window title is filename + abbreviated path. Owns the address-bar navigation logic; back/forward is delegated to WKWebView's native list (see Navigation).
- `fastlane/` - signing + notarization (Fastfile lanes). `make_dmg.sh` builds the dmg.
- `docs-native/` - design/build spec + plan docs.

## Rendering
- Markdown is GitHub-flavored (tables, task lists, strikethrough, autolinks), parsed in-page by bundled `marked.js` and syntax-highlighted by bundled `highlight.js` (~40 languages). Both live in `Sources/MDReader/Resources/`. Fenced ```mermaid blocks are rewritten to `pre.mermaid` and rendered by bundled `mermaid.min.js` (only injected when the source contains a mermaid block).
- `MarkdownRenderer.document(markdownSource:)` injects the raw markdown into a `<script type="text/markdown">` island and parses on load. marked v12 removed the `highlight` option, so code is highlighted by calling `hljs.highlightElement` on each `pre code` AFTER parse (mermaid blocks rewritten first so hljs never touches diagram source). Adding a token: field on `Theme` + default in `.dark` + `add(...)` in `css()`; hljs colors are mapped to the warm palette in `highlightCSS()`, which models Xcode's default scheme — dedicated `syntaxKeyword`/`syntaxType`/`syntaxFunction`/`syntaxNumber` tokens (rose/teal/warm-blue/amber) split keyword vs type vs function/method vs number by role, with strings on `accentSecondary` (sage) and comments on `muted`.
- Adding a new source file or resource requires an xcodegen regen (see Build gotcha below) so the glob picks it up.

## Live reload
- The window auto-re-renders when the open file changes on disk. Only the ONE file currently shown in that window is watched (never other files); empty state, remote-md, and raw web docs are unwatched. `FileWatcher` (`FileWatcher.swift`) wraps a `DispatchSource` file-system-object source on an `O_EVTONLY` fd (main queue), debounced 150ms to coalesce rapid writes. Atomic saves (write-temp + rename, what most editors AND the Write tool do) invalidate the fd via `.delete`/`.rename`; the watcher then polls the path (~2s) until a file reappears and rewatches it, so live reload survives them.
- Wiring lives in `MainWindowController+Navigation.swift`: `syncChromeFromURL()` calls `updateFileWatcher(for:)` on every chrome sync (rebuilds only when the watched path actually changes, so history walks don't churn it). On a change, `reloadCurrentFile()` captures `window.scrollX/Y`, calls `webView.reload()` (re-runs the `mdreader://file` scheme request → re-reads bytes), and the `didFinish` delegate restores the offset via `restorePendingScrollIfNeeded()`. Watcher is torn down in `deinit`.
- Single source of truth = WKWebView's native back-forward list. A `MDReaderSchemeHandler` (`WKURLSchemeHandler`, registered on the config BEFORE the webview is created and retained by the controller — config holds it weakly) serves `mdreader://` URLs as themed HTML, so every app-controlled doc is a real WKWebView back-forward item: `mdreader://empty` (empty state), `mdreader://file?path=…` (local file), `mdreader://remote-md?url=…` (handler async-fetches + themes). Web pages are already real http(s) items. So all navigation (docs and web) lives in one list; `canGoBack`/`canGoForward` = `webView.canGoBack`/`canGoForward`, and `goBack`/`goForward` = `webView.goBack()`/`goForward()`. Crossing the web<->document boundary can't drop web sub-pages.
- `NavBar.swift` - slim address/back/forward bar, hidden by default. `Cmd+L` shows + focuses it (address prefilled with `lastAddressText`, selected); `Esc` hides. `Cmd+[` / `Cmd+]` and the chevron buttons walk history. It sits below the titlebar band so its controls clear the traffic lights. `NavDocument` (in NavBar.swift) is a slim classify/build helper: cases `.empty`/`.file`/`.remoteMarkdown`, each with an `mdreaderURL` (URLComponents percent-encodes the query).
- Relative links/images resolve via `<base href>` spliced after `<head>` by the handler (`file://<dir>/` for files, parent dir for remote-md); MarkdownRenderer stays URL-agnostic.
- Address submit classifies the input via `navigate(toAddress:)`: local path / `file://` -> `loadMDReader(.file)`; http(s) ending in `.md`/`.markdown` -> `loadMDReader(.remoteMarkdown)` (handler fetches + themes); any other http(s) -> `webView.load` raw. Before that classify, a github.com `/blob/…` or web-editor `/edit/…` URL is rewritten to its `raw.githubusercontent.com` equivalent by `canonicalGitHubRawURL` (else the `.md`-suffixed edit URL fetches GitHub's app HTML, not the file).
- In-doc http(s) link clicks (`navigationType == .linkActivated` in `decidePolicyFor`) route through that same `navigate(toAddress:)` classifier, so a clicked `.md` link renders themed and joins the back-forward list. `mdreader://` (handler serves it) and `file://` relative links are allowed in place. Programmatic http(s) loads (raw web nav) pass through.
- Known cosmetic quirk (page-side, not our bug): after Back returns to a GitHub HTML page (blob -> Raw -> themed -> Back), the thin loading bar can stay lit even though the page is fully rendered and usable. The app draws NO progress bar (we KVO only `\.url`, never `\.estimatedProgress`); the lit bar is GitHub's own `.turbo-progress-bar` DOM element left painted after a WebKit back-forward restore where Turbo's completion event doesn't clean it up. Purely cosmetic, GitHub-side; leave as-is.
- Chrome (filePath, title, address prefill, nav buttons) is derived from `webView.url` by `syncChromeFromURL()`, driven by both the nav-delegate `didCommit` (mdreader:// + normal http loads) and a KVO observer on `webView.url` (JS-routed Turbo/`pushState` web sub-navigations that bypass the delegate). `recordOpen()` (dedup-gated by `lastRecordedPath`) fires once per distinct file, so history walks re-committing the same file don't reshuffle recent-files.
- Keyboard-shortcuts cheat sheet: `Cmd+/` (or bare `?`) toggles a themed modal listing all active bindings, injected into the current document's WKWebView by `KeyboardShortcutsOverlay` (JS built from `keyMap.shortcutRows()`, colors inlined from `Theme` so it also looks right on raw web pages). Rows come from the live `KeyMap` so user overrides show. It counter-scales by the inverse of `webView.magnification` (and grows its fixed layer by the zoom factor) so the modal renders at a constant full size regardless of doc zoom. Dismiss via the × close button, Esc, backdrop click, or repeat toggle. Wired: `KeyAction.showKeyboardShortcuts` -> `MainWindowController.toggleKeyboardShortcuts()` (in `+Keys.swift`), plus a Help menu item (`MainMenuBuilder.helpMenuItem` -> `AppDelegate.showKeyboardShortcutsMenuItem`) whose `Cmd+/` key-equivalent shadows the KeyMap binding.
- The `Go` menu (built in `MainMenuBuilder.goMenuItem`) exposes Back (`Cmd+[`), Forward (`Cmd+]`), and Open Location… (`Cmd+L`). Items target the `AppDelegate`, which forwards to `keyWindowController`; `AppDelegate.validateMenuItem` enables/disables Back/Forward from the key window's `canGoBack`/`canGoForward`. These menu key-equivalents shadow the `KeyMap` bindings for the same combos (AppKit consumes the event before the local key monitor), so there's no double-fire — the KeyMap entries still cover windows/edge cases.
- While the address field holds focus the key monitor passes all keys through to it, so bare-key vim bindings (and `Cmd+[`/`]`) don't fire until the bar is dismissed — expected, matches browser behavior. When testing back/forward via `hs`, dismiss the field (Esc) first or the keystroke lands in the field.

## Theming (dark/light variants)
- Two built-in themes: `.dark` (warm "reading lamp") and `.light` (warm paper), both full `Theme` Swift literals in `Theme.swift` AND bundled as full-theme JSON resources (`Sources/MDReader/Resources/theme-dark.json` / `theme-light.json`). The JSON is the color source (per the "colors live in JSON" request); the Swift literal is the guaranteed safe fallback if the bundled JSON is missing/invalid — `.dark` is the ultimate default.
- `enum ThemeVariant { case dark, light }` (Theme.swift) owns the selection: `ThemeVariant.current` getter/setter backed by UserDefaults key `MDReaderThemeVariant` (default `.dark` on missing/unknown); `.toggled` flips it; `.bundledResourceName` / `.fallbackTheme` map a variant to its JSON name / hardcoded literal.
- `Theme.load(variant:)` = decode the bundled JSON into a full `Theme` (fallback to the hardcoded literal + NSLog on any failure, never crash), THEN merge the user's partial `~/.config/mdreader/theme.json` override on top via `ThemeOverride.apply`. `Theme.load()` = `load(variant: .current)`. `MainWindowController.init` calls `Theme.load(variant: ThemeVariant.current)`, baking the active theme into that window once.
- Switching is `Cmd+Shift+D` (KeyAction `.toggleTheme`) or View menu > "Light/Dark Theme". The keybinding routes through `MainWindowController.onToggleTheme` (a closure set in `AppDelegate.track`, mirroring `onOpenInNewWindow`) to `AppDelegate.toggleThemeMenuItem`. `AppDelegate.switchTheme(to:)` flips+persists the variant, then REBUILDS every open window in place: snapshot each `windowState`, create a fresh `MainWindowController(filePath:)` (picks up the new variant), `track` it, `apply(windowState:)` to restore frame/sidebar/zoom, close the old window, re-key the previously-frontmost. (No live restyle; the rebuild is why every surface — webview CSS, sidebar, navbar, window bg — picks up the new theme cleanly. Accept a brief per-window flash; scroll position resets to top.)
- View menu built in `MainMenuBuilder.viewMenuItem` (inserted between File and Go); its toggle item carries the `Cmd+Shift+D` key-equivalent that shadows the KeyMap binding (same no-double-fire pattern as Help/Go). `ThemeMenuDelegate.menuWillOpen` relabels the item to the theme it switches TO and checks it when light is active. `main.swift` passes `toggleThemeAction` + `themeVariantProvider` into `MainMenuBuilder.build`.
- `scrollbarCSS()` (raw web pages) still hardcodes amber literals rather than theme tokens, so a raw web page's scrollbar stays amber-on-transparent under both variants. The markdown view's scrollbar and all mermaid/hljs colors DO follow the active theme's tokens.
- Adding/altering a theme token: add it to BOTH `.dark` and `.light` literals + both JSON files (keep them serialized-identical to their literal) + `css()` + optional `ThemeOverride` field/`apply(to:)` line.

## Session persistence
- `Session.swift` - `WindowState {filePath, frame: CGRect, sidebarVisible, magnification: CGFloat?}` + `Session {windows: [WindowState]}`, Codable to `~/.config/mdreader/session.json` (`magnification` is optional so pre-zoom-persistence session files still decode; nil restores default 1.0) (`load()` never crashes on missing/invalid file, falls back to empty + NSLog; `save()` writes atomically, creates the dir). `MDREADER_SESSION_FILE` env overrides the path (tests redirect it off the user's real session). CGRect encodes as nested `[[x,y],[w,h]]` (Codable default), not a flat 4-array.
- `MainWindowController.windowState` snapshots the window (file/frame/sidebar/magnification); `apply(windowState:)` places the frame, opens the sidebar if it was open, and restores the zoom (clamped to min/max magnification).
- Zoom (webview magnification) also persists globally via UserDefaults key `MDReaderMagnification` (`MainWindowController.persistedMagnification`, clamped getter/setter): every new window's webview inits to the last-used zoom (so opening a different file keeps the size), `adjustMagnification` writes it on every zoom in/out, and it survives relaunch. Per-window session restore may override it via `apply(windowState:)`.
- `AppDelegate` saves the session on `applicationWillTerminate` (all open windows, front-to-back) and restores on a NO-file-arg launch via `restorePreviousSession()` (reopens each window; skips files that vanished; empty windows still restored). Launching WITH a file arg (terminal/Finder/`open -a`) keeps single-window behavior and does NOT trigger restore. One file per window; no tabs.

## File association (default .md handler)
- `project.yml` declares a `CFBundleDocumentTypes` entry for markdown (`net.daringfireball.markdown`/`public.plain-text` content types, `.md`/`.markdown` extensions, `CFBundleTypeRole: Viewer`, `LSHandlerRank: Owner` so MDReader claims preference). Bundle id is `com.binarygap.mdreader`.
- Declaring the type is not enough to become the OS default: set it with `duti`. If a stale/other app holds the UTI, force-register the installed copy first (`lsregister -f /Applications/MDReader.app`), then `duti -s com.binarygap.mdreader net.daringfireball.markdown all` (and `md`/`markdown` for the bare extensions). Verify with `duti -x md` (expect `MDReader` / `/Applications/MDReader.app`).
- Set MDReader default only for markdown types, never `public.plain-text` alone, or it hijacks every `.txt`.

## VS Code extension (`vscode-extension/`)
- Themes VS Code's BUILT-IN markdown preview with this app's theme; contributes `markdown.previewStyles` + `markdown.previewScripts` (plus `extension.js` for the in-place preview toggle). Installed locally by symlinking the dir into `~/.vscode/extensions/binarygap.mdreader-markdown-theme`.
- `MDReader --dump-css <vars|rules|highlight|mermaid-rules|mermaid-config> [dark|light]` (`CSSDump.swift`, checked at the top of `main.swift` before NSApplication) prints stylesheet slices headlessly, so the extension derives its CSS from the app instead of hand-copying colors. `mise run vscode:css` runs `vscode-extension/scripts/build-theme-css.ts`, which composes `media/mdreader-theme.css` (shared rules once; vars + hljs + mermaid rules scoped per variant to `body.vscode-dark` / `body.vscode-light`), `media/mdreader-mermaid-config.js`, and copies the mermaid runtime (git-ignored). Re-run it after any theme change.
- The resolver runs each candidate binary with a 5s timeout because a build predating `--dump-css` ignores the flag and opens the GUI instead of exiting. Swift small-string literals (<=16 bytes) live in code immediates, not `__cstring`, so grepping the binary for the flag does NOT find it.
- `media/mdreader-vscode-preview.css` + `media/mdreader-mermaid-preview.js` are hand-written: they bridge this app's DOM (`.content` wrapper, `pre.mermaid`) onto the preview's DOM (content straight in `<body>`, `language-mermaid` fences) and re-render on the preview's `vscode.markdown.updateContent` event. The 3.4MB mermaid runtime is injected lazily (nonce + URL taken from `document.currentScript`) only for docs that contain a diagram.
- Debug builds need `CODE_SIGNING_ALLOWED=NO` while no "Mac Development" certificate is in the keychain (only "Apple Distribution" is); `mise run ai:xcode_build` fails with a signing error without it.

## Build (dev)
- `mise run ai:xcodegen` - regenerate `MDReader.xcodeproj` from `project.yml` (run after editing project.yml OR adding any new source/resource file, since the project globs). The `mise.toml [env] APPLE_TEAM_ID` resolves to the Developer ID team (`3MAW268EFW`) even in a non-interactive shell, so xcodegen bakes a real `DEVELOPMENT_TEAM` into the pbxproj and the notarized-build export gets a non-empty `teamID`. Verify: `grep -m1 DEVELOPMENT_TEAM MDReader.xcodeproj/project.pbxproj` shows `3MAW268EFW`, not `""`.
- mise.toml env gotcha: `APPLE_TEAM_ID` is templated from `env.MDREADER_TEAM_ID` (default `3MAW268EFW`), NOT from `env.APPLE_TEAM_ID`. A self-named template (`APPLE_TEAM_ID = {{ env.APPLE_TEAM_ID | default(...) }}`) can't inherit an externally-exported `APPLE_TEAM_ID`: mise excludes the key being defined from its own `env` context, so the self-reference always resolves empty and clobbers it -> `teamID:""` in the gym export options -> `build_mac_app` dies with code 9 ("Error packaging up the application", real cause in `~/Library/Logs/gym/MDReader-MDReader.log` + the `xcdistributionlogs/IDEDistribution.standard.log`). To override the team, export `MDREADER_TEAM_ID`, not `APPLE_TEAM_ID`.
- `mise run ai:xcode_build` - debug build via xcodebuild. Output under DerivedData.
- `mise run ai:run [path/to/file.md]` - build (summarized) + launch the debug app against a file (kills any running instance first). After making code changes, this leaves the build updated and running; tell the user so. A `Stop` hook in `.claude/settings.json` runs it automatically at the end of every turn, so you don't need to invoke it manually.
- `mise run ai:dev:screenshot [path/to/file.md]` - build, launch backgrounded against a file, and screenshot the result.

## Notarized build + install to /Applications
- Secrets (`MATCH_PASSWORD`, `MATCH_GIT_URL`, App Store Connect key ids) come from `fnox.toml` (age-encrypted), auto-injected on `cd`. Run the lane under `fnox run` if env isn't already injected.
- `APPLE_TEAM_ID` (Developer ID team `3MAW268EFW`) is templated in `mise.toml [env]` from `{{ env.MDREADER_TEAM_ID | default(value='3MAW268EFW') }}`, so a plain `fnox run -- mise run release:notarized-build` exports a non-empty `teamID` to gym (empty teamID breaks exportArchive -> `build_mac_app` code 9). Don't repoint that template at `env.APPLE_TEAM_ID` (self-named -> always empty) or a bare `""` literal.
- Build: `fnox run -- mise run release:notarized-build`. This wipes `build/`, does the throwaway-keychain dance, signs with `Developer ID Application: Binary Gap LLC (3MAW268EFW)`, notarizes app + dmg via notarytool, staples. Produces `build/MDReader.app`, `.zip`, `.dmg`. Takes a few min (real Apple notary call). Keychain is restored via the lane's `ensure` block even on failure.
- Verify before install: `xcrun stapler validate build/MDReader.app` and `spctl -a -vvv -t exec build/MDReader.app` (expect `source=Notarized Developer ID`).
- Install: `mise run release:install` (pkill running MDReader, `rm -rf` the old /Applications copy, `ditto` the build/ artifact in, re-validate stapler+spctl). It runs automatically as a `depends_post` of `release:notarized-build`, so a fresh notarized build refreshes the installed app on its own; also runnable standalone against an existing build/ artifact.
- The Release archive bundles the current working tree, so an uncommitted change ships in the notarized app. Commit before `release:publish`.

## Publish (GitHub Release)
- `mise run release:publish` pushes branch + tag and creates the release from `build/`. Refuses unless tag `vX.Y.Z` exists and points at HEAD AND matches the built `CFBundleShortVersionString`. Run the notarized build first.

## Conventions
- Theme is the single source of styling; never hardcode colors in CSS strings, add a token. New token = field on `Theme` + default in `.dark` + `add(...)` in `css()` + optional field on `ThemeOverride` + line in `apply(to:)`.
- After UI changes, verify with the XCUITest suite (`mise run ai:test`), not by screenshotting. When you add or change UI behavior, add/adjust a test case in `Tests/MDReaderUITests/` covering it (assert on queryable state via accessibilityIdentifiers, not pixels). Make elements testable by giving them a stable `accessibilityIdentifier` rather than matching on labels/coordinates.
- Two test targets, both in the `MDReader` scheme's test action: `MDReaderUITests` (black-box XCUITest, drives a launched app) and `MDReaderUnitTests` (`bundle.unit-test` hosted by the app via `TEST_HOST`/`BUNDLE_LOADER`, `@testable import MDReader` for logic-only helpers: URL canonicalization, frontmatter strip, mermaid-fence wiring). Pure/logic functions go in the unit target; anything needing real UI/window state goes in the UI target. `mise run ai:test <TargetOrTestId>` requires an explicit `-only-testing` selector arg (e.g. `MDReaderUnitTests`); it does not run all tests with no arg. Adding a test file requires an xcodegen regen (glob) same as any source. Some interactions can't be driven synthetically in XCUITest (e.g. the proximity-hover floating pill relies on real `NSEvent.mouseLocation`); those are documented as uncovered in the test file — verify them manually if you touch them.
- `mise run ai:xcode_build`/`ai:test`/`ai:run`/`ai:xcodegen` wrap the noisy underlying commands and print a compact verdict (success/failure + only the lines that matter); full output goes to `~/.cache/ai-logs/` (both a `<hash>.filtered.log` and the raw `<hash>.log`, paths printed up front), read it only if more detail is needed.
